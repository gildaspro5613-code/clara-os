1. **Références** : un opérateur dans le canal sécurisé existant retrouve la référence de credential, l’identité canonique réelle du propriétaire/reviewer, le workspace et les droits client/projet. La preuve d’exploitation de la boîte doit être indépendante de son adresse et d’un rôle admin OS. Ne pas demander de valeur masquée Vercel ni de mot de passe dans le chat. Si aucune référence n’est trouvée, constater le manque : une injection initiale éventuelle nécessite son propre GO.
2. **Manifeste privé** : pour UNE boîte, faire approuver connectionId historique vérifié ou nouvel ID explicitement alloué après GO (pas dérivé de l’adresse), ownerUserId, reviewer, workspace/client/projet, adresse, référence de coffre, dossiers IMAP et motif de revue. Aucun secret/ciphertext/URL de coffre dans GitHub. Toutes les cases inconnues bloquent l’écriture ; un simple booléen déclaratif ne constitue pas une attestation.
3. **Préconditions de changement** : base effective attestée, point de récupération récent identifiable, rôle opérateur existant limité aux SELECT/INSERT nécessaires, usages mail suspendus, état réseau/monitoring désactivé attesté dans le contexte autorisé. Aucun GRANT ou nouveau coffre supposé disponible. Clé de chiffrement runtime existante, compatibilité et configuration vérifiées sans affichage ; pas de rotation.
4. **Insertion sous GO précis** : le commentaire de migration 016 prévoit l’administration explicite ; aucun appel à mailCredentialStore.save ni contournement de son refus. Paramètres liés par le client existant dans un contexte sûr, jamais collés avec un secret en SQL Editor. Aucun COMMIT n’est fourni : vérifications puis COMMIT seulement sous GO de l’opérateur. Aucun template exécuté dans cette mission.
5. **Vérification expurgée** : exactement un triplet, owner/workspace/adresse/reviewer identiques au manifeste, credential déchiffrable avec la clé existante et conforme à validateMailConfig, aucun curseur/cache/grant de monitoring créé.
