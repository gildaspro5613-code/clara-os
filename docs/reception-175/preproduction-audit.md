Les handlers Google status/connect ne vérifiaient pas la session OS avant lecture/écriture de la connexion globale. Une sonde exécutant les vrais handlers compilés avec repository/OAuth synthétiques a observé, sans cookie : une lecture de statut Google, une écriture de connexion Google et une écriture de credentials Make via configure. Aucun fournisseur appelé. Le callback Google vérifiait nonce/state/provider/connection/workspace, mais pas l'acteur canonique OS. L'inspection montre la même absence de contrôle OS pour Brevo status/connect/callback et Make status/verify ; nonce OAuth et scope de scénario ne constituent pas une autorisation utilisateur OS.

Correction minimale : les neuf routes réutilisent `nativeOperationFence` **avant** body, repository, credentials ou OAuth. Sans cookie, cookie invalide ou doublonné : 401 ; même avec snapshot natif vérifié : 503 `NATIVE_SCOPED_OPERATION_UNAVAILABLE`, `Cache-Control: no-store`, zéro accès aux adapters. Ce verrouillage est intentionnel : il ne prétend pas rendre les connecteurs opérationnels. Les services OAuth, tokens stockés, modèles, Brain et contrats Live sont inchangés. Deux tests couvrent les neuf handlers (27 refus d'authentification et neuf refus de réouverture avec autorité simulée). La CI native inclut désormais ces chemins.

Fichiers applicatifs : `src/app/api/connections/google/{route.ts,connect/route.ts,callback/route.ts}`, `src/app/api/connections/brevo/{route.ts,connect/route.ts,callback/route.ts}`, `src/app/api/connections/make/{status/route.ts,configure/route.ts,verify/route.ts}`. ## Migrations 012 et 013 : prérequis et permissions

Ordre pour les dépendances natives : **001 → 002 → 008 → 012 → 013**, avec vérification préalable du ledger et des migrations déjà appliquées. Les autres parcours conservent leurs dépendances propres (notamment 009/010 pour archivage). Aucun fichier 011 n'existe dans cette base : ne pas inventer une migration ni supposer une séquence complète appliquée.

Vérifier en copie isolée du schéma réel : PostgreSQL compatible, `gen_random_uuid()`, `sha256(bytea)`, `encode`, PL/pgSQL ; tables auth users/workspaces/sessions/memberships/identities ; clients/projets et ACL ; contrainte composite `clara_registry_projects(workspace_id,id,client_id)` ; formes existantes des tables sessions/missions/journal. `CREATE TABLE IF NOT EXISTS` ne corrige pas une table existante incompatible. Les deux scripts ont BEGIN/COMMIT, sont additifs, sans attribution ni backfill de l'historique. 012 crée attestations immuables/révocables et lecture exacte du snapshot ; 013 ajoute scope du Journal et commandes transactionnelles. Réapplication testée localement : historique synthétique non attribué conservé.

Deux rôles distincts à vérifier, sans changer Production :

- Migration : connexion à la base autorisée, CREATE/USAGE du schéma, REFERENCES sur les tables ciblées, propriété ou droits du propriétaire nécessaires pour remplacer fonctions/triggers et REVOKE. Ne pas exécuter sous un rôle client/public.
- Application : USAGE du schéma ; EXECUTE explicite sur `clara_native_read_session(TEXT,TEXT,TEXT,TEXT,TEXT)` et `clara_native_runtime_command(TEXT,TEXT,TEXT,TEXT,TEXT,TEXT,JSONB)` ; SELECT des tables auth/registry et natives utilisées ; INSERT/UPDATE des sessions/missions/attestations et INSERT du Journal/scope. Les verrous FOR UPDATE/FOR SHARE requièrent aussi des privilèges UPDATE appropriés sur les tables verrouillées : workspaces, sessions auth, memberships, identities, clients, projets et leurs ACL. Les grants exacts/colonnes doivent être préparés et testés pour le rôle réel, pas copiés aveuglément comme UPDATE global.

Les fonctions sont **SECURITY INVOKER** et EXECUTE est retiré à PUBLIC ; les nouvelles tables retirent ALL à PUBLIC. Cela n'annule pas les grants déjà accordés à des rôles nommés et ne constitue pas une isolation SQL face à un rôle serveur compromis disposant des tables. Vérifier propriétaires, grants hérités, default privileges, absence d'accès direct des clients à ce rôle et accès minimal. Les deux fonctions de trigger 012 ne retirent pas explicitement EXECUTE à PUBLIC ; elles retournent TRIGGER, pas une API de lecture/mutation autonome. Inclure ce point dans la revue des default privileges, sans revendiquer un durcissement non effectué.

Sonde SQL locale : rôle SELECT+EXECUTE seul refusé sur le verrou de `clara_auth_workspaces` ; après grants de verrouillage synthétiques, la commande atteint le refus canonique `NATIVE_SCOPE_DENIED`. **Le parcours positif sous le futur rôle Neon Production n'est pas testé** ; les tests fonctionnels PostgreSQL existants utilisent le propriétaire de fixture. Ce contrôle reste un gate de réception.

## Priorité Google : contrat manquant, pas simple configuration

Sources : `src/lib/connections/connection.ts`, `connection-repository.ts`, `src/lib/auth/oauth/{types,state,service}.ts`, `src/lib/connectors/internal/google/auth/google-auth.ts`, `src/lib/connectors/google/drive/drive-client.ts`, `src/app/api/native/documents/authorization/route.ts` et migrations 012/013.

La connexion est identifiée par connectionId/provider/workspace, avec unicité workspace/provider ; elle ne stocke pas le propriétaire canonique ni le subject Google vérifié. Le state signé lie provider/connection/workspace/nonce/expiration/redirectPath, mais pas userId. GoogleAuth peut sélectionner le workspace global par défaut ; DriveClient ne reçoit pas un principal autorisé explicite. Les scopes actuels comprennent Drive complet, Calendar, Gmail modify/send/compose, Docs et Sheets : leur présence ne prouve ni consentement minimal ni droits au fichier.

Avant réouverture : réutiliser session OS, memberships et `connections:manage`, lier l'initiation et le callback au même acteur canonique et workspace avec revalidation, enregistrer l'identité fournisseur vérifiée issuer/subject (jamais déduite d'email/nom), établir une délégation explicite si connexion partagée, sélectionner connectionId depuis l'autorité serveur, refuser les fallbacks globaux. Vérifier pour chaque lecture/mutation l'ACL client/projet, l'attestation documentaire, le principal Google connecté, les permissions Drive actuelles et la révision du contenu ; revalider après révocation/changement de compte. Ne pas utiliser un nom de dossier comme preuve d'appartenance. Les documents Drive partagés nécessitent un cas de recette spécifique.

Toute persistance additive de ce lien doit être conçue sur les registres existants, avec migration distincte à examiner si nécessaire ; **012/013 ne fournissent pas cette association OAuth**. Pas de nouvelle architecture d'identité ni rattachement automatique des anciennes connexions. L'API documentaire retourne 403 pour absence/étranger ; un binding OS reconnu retourne 409 avec `readAllowed:false`, droits Drive/révision non prouvés. Ces protections sont conservées.
