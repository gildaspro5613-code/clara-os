## Protections

- `src/instrumentation.ts` rend le hook détectable à côté de `src/app`. Avant les handlers Node, le profil exige le target Vercel **exact** `clara-os-recette`, `VERCEL_ENV` différent de `production`, `VERCEL=1` et `CLARA_RECETTE_MODE=isolated-v1`. Profil demandé mais incohérent : échec de démarrage, pas de mode dégradé permissif. Tout processus Vercel non-Production aux métadonnées/flag incomplets est également refusé, pour éviter un fallback vers les transports réels. Hors de ces contextes, aucun transport n'est modifié.
- La base est limitée à `neondb`, rôle `clara_os_recette_limited`, TLS obligatoire, endpoint Neon explicitement attesté, branche déclarée figée `br-crimson-feather-b2zr00sf`. `POSTGRES_URL`, options de redirection de connexion et ambiguïtés sont refusés. Le hostname **doit être attesté par l'opérateur comme appartenant à cette branche** : une constante branch ID ou le nom `neondb` ne prouve pas ce lien à elle seule.
- Fetch ne permet que POST `/sql` au endpoint HTTPS calculé par le SDK Neon, avec l'en-tête de connexion correspondant exactement à la connexion de recette validée ; redirects refusés. TCP/TLS sont refusés hors de ce transport SQL et de son contexte asynchrone. UDP et exécutions de sous-processus sont refusés. Les transports existants IONOS, Make, Live et UDP physique ont aussi un refus explicite avant remise. Cette barrière protège les chemins Node du dépôt ; ce n'est pas un bac à sable contre un module natif malveillant ou du code arbitraire ajouté ultérieurement.
- Les routes cron/intake/purge refusent toute invocation en recette, même avec un secret cron valide. Google work POST est refusé avant réserve/approbation ; démarrage OAuth Google/Microsoft refusé. Les autres transports fournisseur sont arrêtés à la frontière réseau. Aucun accusé fournisseur synthétique n'est produit.
- Clara conserve son runtime/Brain et sa persistance ; le connecteur OpenAI rend une réponse locale fixe, marquée `[RECETTE — simulation locale]`, sans appel ni outil ni identifiant fournisseur. Ce mode vérifie la continuité métier, **pas la qualité d'une inférence OpenAI réelle**. Le bandeau de l'interface le rappelle.
- `/recette` permet seulement de poser le cookie d'une session canonique **déjà délivrée** dans la base de test. Le POST revalide expiration/révocation et membership par le résolveur existant, exige même origine HTTPS et corps borné ; pas de création de compte, session, owner, client ou ACL, ni identité déduite d'un email. Cookie Secure/HttpOnly/SameSite ; secret jamais journalisé. Hors recette : 404 ; en configuration Production contradictoire : refus. Les identités et autorisations du scénario restent à préparer par un opérateur autorisé, dans la seule base de test, sans réutiliser une session Production.
- La copie de base peut contenir des credentials et jobs historiques : ne pas les déchiffrer ni les envoyer ; les barrières restent actives même si des variables fournisseur sont héritées. Ne pas copier automatiquement les variables Production.

## Rôle limité et initialisations

Les fonctions SQL natives restent SECURITY INVOKER : CONNECT, USAGE, EXECUTE des fonctions/helpers invoqués et DML ciblé sur leurs tables sont nécessaires. Verrous SELECT FOR UPDATE : UPDATE approprié. Authentification de recette : SELECT sur sessions/memberships ; cet adaptateur ne demande aucun INSERT. Les droits métier restent ceux de 012–020, dont registres/ACL, sessions, missions, Journal/scope, historiques, acquisition et jobs/reçus/approbations. Exécuter **après autorisation** [le contrôle de catalogues préparé](recette-role-check.sql) sous le rôle limité de la seule branche de test. Aucun GRANT global ni privilège administratif proposé.

Le code natif utilise ses stores scoped ; aucune nouvelle initialisation DDL n'est ajoutée. Les anciens initialiseurs de connexions/credentials/journal restent hors de ce parcours. Ne pas accorder CREATE sur public pour les faire passer ; si une route les sollicite réellement, signaler son erreur précise et corriger cet initialiseur, pas les droits de tout le schéma. Les permissions effectives Neon n'ont pas pu être inspectées ici : le secret est exclusivement dans Vercel et n'a pas été extrait. Les acquis du propriétaire sur les migrations et permissions initiales restent conservés.
