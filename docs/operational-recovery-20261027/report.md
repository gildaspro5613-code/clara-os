## A — Consultation, missions et continuité
Cause : orchestrate() convertissait chaque cycle en Mission et persistait ; hydrateSession() pouvait réactiver une mission bloquée ; la boucle autonome pouvait ensuite la modifier. Correction : USER_MESSAGE informatif/ambigu reste non-mutant par défaut ; seuls les verbes de commande explicites reconnus autorisent le pipeline de planification existant. Les événements métier typés conservent leur chemin. Le modèle n'est pas une source d'autorisation. Les commandes non reconnues restent des consultations : l'utilisateur peut employer les commandes explicites ou les contrôles Mission existants. Aucun classificateur probabiliste ni nouveau moteur.

La conversation, la réponse et le Journal cognitif restent persistants ; sans modification de l'identité, des tâches, de la progression ou du statut de mission lors d'une consultation. L'absence de mutation de mission n'est pas l'absence d'écriture de conversation.

Dépendance démontrée par PostgreSQL : 017/019 interdisaient toute reprise d'un fil sans mission après un premier échange. La migration additive 030 remplace uniquement la définition de l'inner runtime installé par 019 et renommé par 025. Elle refuse toute définition interne différente de la base 019 attendue ou de sa propre version (empreintes de code SQL, sans secret). Elle conserve les wrappers 025/026, l'autorité, les contrôles CAS, les ACL et l'archivage existants. Le protocole de consultation absent est refusé avant cognition dans un fil sans mission (NATIVE_CONSULTATION_MIGRATION_REQUIRED). Une certification numérique de consultation est ajoutée côté SQL après les vérifications existantes, sans backfill, nouveau store ou GRANT. Un historique sans preuve ne peut pas s'attribuer cette certification. Les sessions liées à une mission restent immuables dans leur identité ; une consultation passée ne reçoit pas silencieusement une nouvelle mission. Pour créer après un historique sans mission, créer explicitement un nouveau fil avec les contrôles existants. Le refus est signalé par le message existant dans le chat.

Progression 29 %/38 % : les cartes/détails recalculent completed/tasks ; Cockpit/composer lisent mission.progress ; MissionDetail conserve aussi des tâches en état local. L'écart précis de Production n'est pas reproduit sur une même révision. Aucune correction de progression spéculative. Lecture ciblée future : même missionId, révision, nombre total/terminé, mission.progress, horodatage des deux vues, sans contenu métier. Comparer les projets/sessions avant toute conclusion.
